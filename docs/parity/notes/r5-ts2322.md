# r5-ts2322: the sole-TS2322 cases

Lane on epic `tsr-2zk`, vendor `5b1047d`. Target: the diagnostics cases whose
**only** wrong code is TS2322 — the expected-minus-actual and
actual-minus-expected multisets both contain nothing but `2322`.

Frozen baseline: integration head `d91243e`. Diagnostics dump 5399 RIGHT,
1192 WRONG, 5584 EMPTY_RIGHT, 63 EMPTY_WRONG. On that tree 123 cases are
sole-TS2322 (the integrator's 136 is an earlier head): 121 plain and two
configured rows (`argumentsBindsToFunctionScopeArgumentList(alwaysstrict=true)`,
`divergentAccessorsTypes3(target=es2015)`). 89 miss a line, 39 carry an extra
one, 5 both. TS2322 is missing in 139 cases with any wrong code and extra in 73.

## Method

Same as [r5-missingprop](r5-missingprop.md) §1. Every differing line of the
121 plain cases came from `examples/r5census.rs` under `TSR_ASSIGN_PROBE=1`
(`CODES=2322`; 218 lines, 137 missing and 81 extra),
which names the `report_assignability_failure` gate for each missing line:
`NEVER` (no report asked at that position — a check site or an elaboration
that never ran), `DECLINED` (the relation answered `Unknown`),
`NOTREPORTABLE` (the pair gate refused an `any`/gap side). Each cluster was
then reproduced as a minimal file and run through both `target/release/tsr`
and a native `tsgo` built from the pinned submodule
(`scripts/offline-cargo/build-tsgo.sh`); the "witness" column names the case
whose line was reproduced.

| side | gate | lines | cases |
|---|---|---|---|
| missing | `NEVER` | 71 | 48 |
| missing | `DECLINED` | 48 | 32 |
| missing | `NOTREPORTABLE` | 18 | 12 |
| extra | – | 81 | 38 |

Classes, as the brief defines them: (a) the relater answers Related/Unknown
where native answers False; (b) a missing check site; (c) the wrong source
type; (d) the wrong target type; (e) placement or elaboration; (f) an extra
report from a false NotRelated.

## 2. Fixed here

### 2.1 The destructuring-assignment relation (T1)

`checkDestructuringAssignment` (`checker.go:12552`) walks an array or object
literal target top-down with the source type and ends every leaf at
`checkReferenceAssignment` (`checker.go:12704`), which relates the slice to
`checkExpression(target)` at the target. `reference_target.rs` ported only
the walk's `checkReferenceExpression` half, so `let a: string; [a] = [1]` was
silent. `destructuring_assignment.rs` is the relation half, reached from the
same two entry points (`=` with a literal left, and a `for…of` literal head,
whose source is `checkRightHandSideOfForOf`'s element):

- object property: `getIndexedAccessTypeEx(source, name, ExpressionPosition |
  AllowMissing-if-defaulted)` through `destructure.rs`'s
  `destructuring_property_lookup`, the binding-pattern road for the same
  lookup; last rest: `getRestType` (`concrete_rest_type`);
- array element: positional `getIndexedAccessTypeOrUndefined` on an
  array-like source (`binding_parent_is_array_like`), else the iterated
  element (`undefined` added under `noUncheckedIndexedAccess`); last rest:
  `sliceTupleType` when every constituent is a tuple, else an array of the
  in-bounds element;
- a defaulted target strips `undefined` under `strictNullChecks`; a shorthand
  `{ x = d }` strips it only when `d` cannot be `undefined`, and also assigns
  `d` to `x` (`checkBinaryLikeExpression(name, =, initializer)`), which is the
  second TS2322 native prints at the same position in
  `destructuringAssignmentWithDefault2` 11:4;
- the target type is `assignment_target_type`, the `=` arm's reader with its
  declines (`const`, auto-typed, enum/class/function/module/alias targets).

Any slice this port cannot compute (`errorType` from the destructure.rs
queries) declines that target and everything under it.

**`getFlowTypeOfDestructuring` is not ported, and is declined soundly.**
Native relates `getFlowTypeOfReference(R["name"], slice)`, a synthetic
element access whose flow node is the right operand's
(`getSyntheticElementAccess`, `checker.go:17857`). The first measurement
without it lost `destructuringControlFlow` (RIGHT → WRONG): `if (obj[0] &&
obj[1]) { ([c0, c1] = obj); }` relates the narrowed `number`/`string` natively
and the declared `number | null` here. This port's flow walker matches real
nodes only (`flow.rs`, main's), so the faithful fix is there (§4). Until
then: the synthetic access exists only when `R` has a flow node, and its flow
type differs from the slice only where some flow node matches `R.name` /
`R["name"]` — a condition on, or assignment to, an access written on `R` in
`R`'s scope (an assignment to `R` itself resets to the declared slice). The
walk scans `R`'s declaration's enclosing function (or file) once and declines
exactly the first-level names accessed there; all names when `R` is not a
plain identifier or is indexed by a non-literal key. Deeper slices inherit
their first-level answer (`R.a.b` contains `R.a`). Rest slices are never
narrowed natively, and a `for…of` head has no synthetic access
(`getParentElementAccess` has no arm for it).

The second measurement lost `destructuringTuple` too: `[...receiver] = tuple`
with `tuple: [boolean, number, ...string[]]` built an array, because the
tuple test read only `tuple_element_lists`; a variadic tuple is in
`variadic_tuple_elements`. Both maps are read now, through the alias body as
`binding_rest_tuple_slice` reads it.

Probed against native on array/object/nested/rest/shorthand-default/for-of
targets, tuple and variadic sources, and guarded and unguarded right
operands: every line TSR prints matches; the guarded slice is the one
declined (native prints nothing there).

Measured: +9 diagnostics cases (`destructuringAssignmentWithDefault2`,
`for-of47`, `for-of48`, `iterableArrayPattern5`/`6`/`7`/`8`,
`noUncheckedIndexedAccessDestructuring`, `nonIterableRestElement3`), no
verdict loss; types dump unchanged (545,161 RIGHT). Two wrong lines are
gained in already-WRONG cases: `awaitedType`/`awaitedTypeStrictNull` 39:9 and
40:9, where `[aaa, bbb] = await Promise.all([MaybePromise(1), …])` relates a
source TSR computes wrongly — it resolves `Promise.all`'s array overload
(`MaybePromise<string> | MaybePromise<number> | …` per element) where native
resolves the tuple overload. That is calls/inference (main's), not this
relation. Still declined: `objectRestNegative` 6:10, whose rest slice is a
minted rest type the relater answers `Unknown` against `{ a: string }`.

Gates: both loss checks empty; slowcases clean on both dumps. Perf, median
child CPU new/old: domain-model 1.026 at 41 samples (1.074 at 21, re-run per
protocol; the project has no destructuring assignment), generic-imports 0.987
at 21. Callgrind Ir new/old: domain-model 0.9987, generic-imports 0.9999.
